description: "Piping a TTY-aware preview command (e.g. chafa) through more breaks it — the command detects a non-tty and renders in a degraded mode, and more miscounts ANSI-escape-padded line widths, causing incorrect pagination."
status: needs-triage

## Problem Statement

`015-per-extension-preview.md` lets a user map a file extension to any preview command via `~/.config/dired`. That works well for text-oriented tools (`glow`, `jq`), but breaks for terminal-graphics tools like `chafa`: the configured command's stdout is piped into `more`, so from the command's point of view its output is going to a pipe, not a real terminal. Two things go wrong at once because of that. First, tools like `chafa` check `isatty()` on their own stdout to decide what quality/color mode to render in — seeing a pipe, they fall back to a conservative low-fidelity mode instead of the full-color output they'd give a real terminal, so an image preview comes out as a blurry, washed-out render instead of a clean one. Second, `more` doesn't understand ANSI color-escape sequences when measuring line length, so a line padded with color codes reads as far wider than the terminal actually is, and `more` wraps it into extra lines — turning what should be one screen's worth of image into several pages of garbled output. Neither problem is fixable by tuning the configured command's own flags; it's a structural mismatch between what a TTY-aware program needs (a real terminal) and what a pipe-into-a-pager gives it.

## Solution

Replace `more` as the pager for every preview path — plain text preview, binary/hexdump preview, and per-extension configured commands alike — with a mechanism that gives the producing command a real pseudo-terminal (pty) when it has one, and pages the result through `less -R` instead of `more` (since `less -R` correctly measures color-escape-padded line widths and gives the same familiar space/q/arrow/search navigation `more` already provides). If pty allocation itself isn't available in the current environment (e.g. a restricted container without `/dev/pts`), the mechanism transparently falls back to exactly today's behavior — a plain pipe into `more` — with no error shown, since the fallback already reproduces the experience users have today. No change to `~/.config/dired`'s file format is needed; every existing rule benefits automatically, with zero migration.

## User Stories

1. As a user who configured a TTY-aware tool like `chafa` for image preview, I want the preview to render at full color/quality when I press Space, so that I see a clean image instead of a degraded, washed-out render.
2. As a user, I want a preview taller than one screen (image or otherwise) to be genuinely scrollable within dired, so that I can see all of it, not just what fit on the first screen.
3. As a user, I want to navigate any preview — text, hexdump, or a configured tool's output — with the same familiar keys (space/q/arrows/search), so that the experience is consistent regardless of what's being previewed.
4. As a user, I want this improvement to apply automatically to my existing `~/.config/dired` rules, so that I don't have to edit or rewrite anything to benefit.
5. As a user, I want plain text and binary/hexdump preview (the built-in default, for files with no matching rule) to get the same paging improvement as configured rules, so that all previews behave consistently rather than only the newer, configurable ones.
6. As a user, if pty allocation isn't available in my environment, I want preview to still work via today's plain-pipe/`more` mechanism instead of failing outright, so that a missing pty capability doesn't take away preview entirely.
7. As a user, I want that fallback to happen silently, with no extra error message, so that a recoverable environment limitation doesn't interrupt me with noise.
8. As a user, I want archive-member previews to get this same improvement automatically, so that a TTY-aware tool configured for, say, `.png` files works the same whether I'm previewing a real file or one inside an archive.
9. As a user, I want `$COL` substitution to keep working exactly as it does today, so that sizing-aware commands (like an image renderer) still receive the correct terminal width regardless of which paging path is used.
10. As a user, I want quitting the pager to return me cleanly to the file listing with no lingering processes, exactly like preview already behaves today.
11. As a developer, I want the pty-based execution path and the plain-pipe fallback path implemented as independently callable functions, so that each can be verified with real subprocess integration tests rather than relying on a human watching a terminal.
12. As a developer, I want the fallback-selection logic (pty succeeded vs. pty allocation failed) to be deterministically testable, so that the fallback trigger itself has real automated coverage, not just each underlying path tested in isolation.
13. As a developer, I want this change to require zero modifications to config parsing, extension matching, or argv-building (`parse_preview_rules`, `match_preview_rule`, `build_preview_argv`), so that the already-shipped, already-tested config layer stays untouched — this PRD only changes how an already-selected command gets executed and displayed.
14. As a developer, I want no new `~/.config/dired` syntax introduced, so that the file format documented in `015-per-extension-preview.md` remains fully valid with no migration step.
15. As a developer, I want archive-member preview (`execute_open_archive_member`) to require no code changes of its own, so that it inherits this improvement purely by virtue of already delegating to the same preview-execution path.
16. As a developer, I want detection of an `execvp` failure inside a child process (e.g. `chafa`, `less`, or `more` not being installed) to be explicitly out of scope here, so that this work stays focused on the pty/pager mechanism rather than growing into general error-message handling (tracked as a separate, later PRD).

## Implementation Decisions

- **Three composable pieces replace today's single `more`-only pipeline**:
  - `run_via_pty(primary_argv, pager_argv)` — allocates a real pty (via `forkpty()`), execs the primary/producer command with its stdout/stderr attached to the pty slave, and pipes the pty master into the pager command. Mirrors the existing `run_piped()`'s "fork two children, wait on both" shape, just with a pty in place of a plain `pipe()` on the producer side.
  - `run_via_pipe(primary_argv, pager_argv)` — the existing `run_piped()` mechanism, used unchanged as the fallback.
  - `run_paged(primary_argv, pty_pager_argv, pipe_pager_argv)` — orchestrator. Attempts pty allocation first; on success, delegates to `run_via_pty`. On pty-allocation failure specifically (not on a downstream exec failure inside the child, which stays undetectable by the parent as discussed below), transparently delegates to `run_via_pipe` with the fallback pager argv. No error is surfaced for this fallback — it's a deliberate, silent degrade to today's already-working behavior.
- **Pager selection**: the pty path always pages through `less -R` (or `-r`, whichever flag proves correct for the color-escape sequences these tools emit); the fallback path always pages through `more`, matching today's behavior exactly.
- **Applies to three call sites, uniformly**:
  - Per-extension configured rules (the matched-rule branch already shipped in `015-per-extension-preview.md`'s `execute_preview` integration) — swaps its existing `run_piped(argv, {"more", NULL}, NULL)` call for `run_paged(argv, {"less", "-R", NULL}, {"more", NULL})`.
  - The default binary/hexdump preview (currently `run_piped(hexdump_argv, pager_argv, NULL)`) — same swap.
  - Plain text preview (currently a direct `execlp("more", "more", path, NULL)` with no producer/pipe at all) — since nothing here depends on tty detection (there's no separate producer process whose rendering quality changes based on `isatty()`), this simplifies to a single direct exec of `less -R path`, with no pty allocation and therefore no fallback branch needed for this specific case; if `less` itself isn't installed, that's the same kind of invisible exec failure already out of scope for this PRD (see below), and behaves the same as if `more` were missing today.
- **Config layer untouched**: `parse_preview_rules`, `match_preview_rule`, and `build_preview_argv` (all already shipped) require no changes. This PRD only changes what happens after a command has already been selected and its argv already built.
- **No new config file syntax.** `~/.config/dired`'s existing `ext=command $FILE` format is unchanged; every existing rule benefits automatically.
- **Archive-member preview requires no changes** — `execute_open_archive_member` already delegates to the same preview-execution path for both edit and preview, so it inherits this improvement without any code of its own changing.
- **Failure surfacing**: pty-allocation failure is handled by the silent fallback described above — no `msg_failed`/`MODE_ERROR` involved, since a working, already-proven fallback exists for this specific step. This is a deliberate exception to a general "surface failures visibly" push considered during design: it only applies where there's no recovery path at all, which isn't the case here.
- **Exec failure inside either child** (the configured command, `hexdump`, `less`, or `more` itself failing to `execvp`, e.g. because it isn't installed) remains invisible to the parent process, exactly like today's `run_piped`-based pipeline. This is a known, pre-existing gap (not introduced by this PRD) and is explicitly deferred to a separate future PRD covering proper error-message handling across all preview/exec paths — not designed here.
- **Build**: `forkpty()` (declared in `<pty.h>`) needs `-lutil` linked on Linux; it's already part of the system library on macOS, so no extra linking is needed there. The build's existing (currently empty) `MACOS_FLAGS` constant is the natural place to keep this platform difference isolated.

## Testing Decisions

- Good tests here are real subprocess integration tests — exercising actual `fork`/`exec`/pty syscalls end-to-end with trivial real commands — rather than mocking OS calls, consistent with this codebase's general avoidance of mocking I/O. This is a deliberate, narrowly-scoped exception to the convention (established across `002`, `005`, and `015`) that all fork/exec/filesystem code in `dired.c` goes untested: the pty machinery here is new and meaningfully riskier than the plain-pipe code that came before it, and unlike that code, its correctness genuinely can be verified without a human watching a terminal.
- **`run_via_pty`** and **`run_via_pipe`**: each tested independently with trivial real commands standing in for the real tools (e.g. a `printf`-style producer, and a pager stand-in that just writes what it receives to a temp file rather than `less -R`/`more`), asserting the exact bytes the producer wrote arrive intact on the pager side. No prior art for this exact shape in the codebase (`run_piped` was never tested), but it mirrors the "assert on concrete output" style already used for `parse_preview_rules`/`match_preview_rule`/`build_preview_argv`'s table-driven tests, just at the integration level instead of the pure-function level.
- **`run_paged`** (the orchestrator): its fallback-selection logic needs one narrow, deliberate test seam — the pty-allocation step is swappable (a function pointer), with the real `forkpty()`-based implementation used in production and a stub that always reports allocation failure used only in tests. One test supplies the failing stub and asserts output correctly flows through the pipe/fallback pager stand-in (proving the fallback both triggers and still produces correct output); another exercises the real/success path and asserts output flows through the pty/pager stand-in instead. This is the only dependency injection introduced by this PRD, scoped exclusively to making the fallback trigger deterministic in tests — nothing else in the codebase gains a mocking seam because of this.
- **Explicitly not automated, and not expected to be**: whether a specific real-world tool like `chafa` renders a visually correct or attractive image, and whether `less`'s interactive navigation (space/q/arrows/search) feels right in practice. Both require a human at a real terminal; no test in this PRD's suite is designed to catch "the image looks wrong" or "scrolling feels off" — those get verified manually by whoever implements this, not by an agent (agents cannot observe rendered terminal output per this repo's own "Note for AI agents working in this repo" in `Readme.md`).
- **New test file needed**: since these tests exercise `src/dired.c`-level fork/exec logic rather than `src/helpers.c` pure functions, and no test file currently covers any of `dired.c`'s process-oriented code, this will need a new test file (following the existing `test/*_test.c` + `test/main.c`/`test/tests.h` wiring convention) — itself a small new precedent, since `dired.c`'s fork/exec code has never had test coverage of any kind before this PRD.

## Out of Scope

- Any change to `~/.config/dired`'s file format or syntax — this PRD is purely an internal execution-mechanism change.
- Detecting or surfacing an `execvp` failure inside a child process (a configured command, `hexdump`, `less`, or `more` itself missing or failing to exec) — this is a pre-existing gap in `run_piped` today and stays a gap after this PRD; tracked as a separate, later PRD on general error-message handling across all preview/exec paths.
- Any change to config parsing, extension matching, or argv substitution (`parse_preview_rules`, `match_preview_rule`, `build_preview_argv`) — all already shipped and unaffected.
- Any change to archive-member extraction or temp-file naming (`extract_member_to_tmp`, already shipped in `015-per-extension-preview.md`) — this PRD only changes how an already-extracted file gets previewed.
- Automated verification that a specific external tool's rendered output looks visually correct, or that `less`'s interactive navigation feels right — inherently human-only verification, not something this PRD's test suite attempts.

## Further Notes

This PRD revisits and reverses `015-per-extension-preview.md`'s Out-of-Scope line — "Any change to the pager itself — matched and unmatched files alike still page through more" — now that a concrete need (TTY-aware preview tools rendering incorrectly) and a working mechanism (pty + `less -R` with automatic fallback) both exist. Consistent with that PRD's own precedent, the change is applied uniformly to matched and unmatched files alike, not special-cased per rule.

A second, explicitly separate PRD is planned to cover proper error-message surfacing for exec failures across all preview/exec paths — both the pre-existing gap in `run_piped` and the new pty path introduced here. It is intentionally not designed as part of this PRD, to keep this one scoped to the pty/pager mechanism itself.
